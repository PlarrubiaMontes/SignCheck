# SignCheck — guide for Claude Code

## What this project is

SignCheck is an open-source web application that validates advanced electronic signatures
(**PAdES, XAdES, CAdES** and, optionally, **ASiC** containers) following eIDAS and ETSI standards.
It is built on top of the European Commission's **DSS (Digital Signature Services)** library.
A later phase adds signature creation with self-generated test certificates.

It is a **personal portfolio project** by Pedro, a Java/Spring Boot developer who works with
digital signatures. Clarity, code quality, tests and explainability matter more than the number
of features.

Detailed docs (read them before starting any task):

- `docs/SPEC.md` — functional requirements and REST API contract
- `docs/ARCHITECTURE.md` — modules, packages, DSS integration, test PKI
- `docs/ROADMAP.md` — phases and tasks with acceptance criteria (source of truth for "what's next")

## Hard rules

1. **No real certificates, private keys, personal data or real signed documents** anywhere in the repo.
   All test material is generated by the test PKI (see `docs/ARCHITECTURE.md` → Test PKI).
2. **No code, documents, names, endpoints or configuration from Pedro's employer or its clients.**
   Everything is written from scratch, based only on public standards and public libraries.
3. **No secrets in the repo.** Test keystore passwords are test-only and must be labelled as such.
4. **DSS types never leak into the REST API.** Map DSS reports to our own DTOs.
5. **Every feature ships with tests.** A task is done only when `./mvnw verify` (backend) and
   `npm test` + `npm run build` (frontend, once it exists) pass.
6. **Tests never need internet.** LOTL download, OCSP, CRL and TSA access sit behind configuration
   or interfaces and are replaced by offline sources in tests.
7. **Check versions and APIs against official sources** (Maven Central, DSS documentation, Spring docs)
   instead of relying on memory. DSS APIs changed between major versions (5.x → 6.x).
8. Uploaded files are processed **in memory and never persisted or logged** (log metadata only: size, detected format).

## Tech stack

- **Backend:** Java 21, Spring Boot (latest stable version compatible with DSS), Maven with wrapper (`./mvnw`)
- **Signatures:** EU DSS 6.x (latest stable; must support Trusted List v6), imported through `dss-bom`
- **API docs:** springdoc-openapi (Swagger UI)
- **Tests:** JUnit 5, AssertJ, MockMvc, BouncyCastle (test PKI)
- **Frontend:** Angular (latest stable; standalone components, signals), Angular Material or plain SCSS
- **Infra:** Docker multi-stage builds, `docker-compose`, GitHub Actions CI

## Commands

Backend (from `backend/`):

```bash
./mvnw spring-boot:run                 # run on :8080 (profile "dev": trust mode "none")
./mvnw verify                          # build + all tests
./mvnw test -Dtest=PadesValidationTest # single test class
```

Frontend (from `frontend/`):

```bash
npm ci
npm start        # dev server on :4200, proxies /api to :8080
npm test
npm run build
```

Whole stack:

```bash
docker compose up --build   # frontend on :8081 (nginx), backend behind /api
```

## Code conventions

**Java**

- Package by feature (`validation`, `trust`, `signing`), not by layer.
- Constructor injection only. No field injection. No Lombok: use `record`s for DTOs and value objects.
- Configuration through typed `@ConfigurationProperties` (prefix `signcheck`), never scattered `@Value`.
- Errors: one `@RestControllerAdvice` returning RFC 9457 `ProblemDetail` with a stable `code` property.
- Keep controllers thin: HTTP ↔ DTO only. Logic lives in services; DSS calls live behind our own classes.
- Test names describe behaviour: `shouldReportInvalidWhenDocumentWasModifiedAfterSigning()`.
- Javadoc on public classes of the `validation`, `trust` and `signing` packages explaining the signature concept involved (this doubles as learning material).

**Angular**

- Standalone components, signals for state, typed `HttpClient` services, strict TypeScript.
- API models in `src/app/core/api/` mirror the backend DTOs.
- UI texts through i18n (English and Spanish).

**Git**

- Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `refactor:`, `ci:`).
- One task from the roadmap ≈ one or a few commits.
